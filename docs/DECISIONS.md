# 架构与需求决策

## ADR-001：完成定义优先级

- 状态：已接受
- 决定：第 19 节以及目标文件显式补充的设备、签到签退、并发、审计、测试、备份恢复和部署均为必做。
- 原因：目标文件明确解决了第 1.2 节“加分扩展”与第 19 节之间的范围冲突。

## ADR-002：管理员预约身份

- 状态：已接受
- 决定：纯管理员不能创建预约；只有同时具有 `STUDENT` 或 `TEACHER` 业务角色的账号才能预约，类别由后端身份生成。
- 原因：遵循第 1.3、2.2 节和目标文件的显式解释，修正第 9.1 节路由表的宽泛描述。

## ADR-003：会话与 CSRF

- 状态：已接受
- 决定：Access Token 由前端仅保存在内存；Refresh Token 使用 HttpOnly Cookie，数据库只存 SHA-256 摘要；刷新接口采用双提交 CSRF Token，生产 Cookie 启用 Secure 和 SameSite=Strict。
- 原因：兼顾 SPA 使用体验、令牌泄露面和刷新请求 CSRF 防护。

## ADR-004：性能工具

- 状态：已接受
- 决定：性能脚本使用 k6，并通过固定版本 Docker 镜像执行，不依赖宿主机安装。
- 原因：当前环境未安装 k6，容器方式可重复且满足“不使用 latest”。

## ADR-005：PostgreSQL 集成测试运行方式

- 状态：已接受
- 决定：同一个无跳过的 Flyway 集成测试优先读取一次性外部测试数据库；未提供时使用 `postgres:16.15-alpine3.24` Testcontainers。Windows 统一验证脚本在 Docker 不可用时，以本机 PostgreSQL 16 二进制创建并销毁一次性集群。
- 原因：当前 Docker Desktop 因 WSL 未启用而无法运行，但本机具备 PostgreSQL 16；该方式仍真实验证 PostgreSQL 语义，并保留 CI/Testcontainers 路径。

## ADR-006：统计口径与同步导出边界

- 状态：已接受
- 决定：总览的有效预约和利用率分子只计算当前为 `APPROVED`、`IN_USE`、`COMPLETED` 的预约；利用率分母按统计区间内启用课次、实验室开放规则和停用课次实时展开。同步 CSV 使用完全相同的日期、实验室、申请人类型和状态筛选，超过 `export.max-rows` 时拒绝并要求缩小范围。
- 原因：与开发文档第 3.9 节的明确公式一致，并保证统计可由预约明细复算；第一阶段上限为 10,000 行，无需引入超出范围的异步大导出基础设施。

## ADR-007：容器网络与对外边界

- 状态：已接受
- 决定：PostgreSQL 仅加入数据网络，后端同时加入数据与 Web 网络，Nginx 仅加入 Web 网络；生产仅发布 Nginx TLS 端口，Actuator、OpenAPI 与数据库不经 Nginx 暴露。应用容器使用固定 UID、只读根文件系统和临时目录。
- 原因：以网络隔离和单一入口缩小攻击面，同时保留容器内健康检查和 Prometheus 抓取能力。

## ADR-008：备份文件保护与恢复验收

- 状态：已接受
- 决定：`pg_dump` 自定义格式在离开数据库容器后立即使用 AES-256-GCM 加密；密钥由环境变量提供并经 PBKDF2-HMAC-SHA256 派生。恢复必须显式指定目标库，默认拒绝覆盖；验收恢复到新库并比较预约与审计的行数和内容摘要。
- 原因：备份可能包含个人与审计数据，不能以明文落盘；新库与指纹核对可同时证明可解密、可恢复和核心数据一致。

## ADR-009：限流边界

- 状态：已接受
- 决定：登录按来源 IP 每分钟 30 次，其余已认证请求按 Access Token 摘要每分钟 600 次；返回统一 `RATE_LIMIT_EXCEEDED`、请求 ID 和 `Retry-After`。不保存原始令牌。
- 原因：登录需要更严格的暴力尝试保护，而业务请求需要容纳 SPA 并发；令牌摘要兼顾用户粒度与秘密最小暴露。

## ADR-010：性能场景认证方式

- 状态：已接受
- 决定：性能种子创建 10,000 名专用测试用户和 200 个实验室；k6 使用仅在隔离性能 Compose 中配置的测试 JWT 密钥为各虚拟用户签名短期令牌，不把 BCrypt 登录耗时混入业务接口阈值。
- 原因：验收目标是空闲查询、预约提交和统计接口的业务延迟；逐用户登录会测试密码哈希吞吐而扭曲目标，同时专用隔离密钥不会进入生产配置。

## ADR-011：300 在线用户负载模型

- 状态：已接受
- 决定：k6 在 20 秒内逐步升至 300 VU，保持 300 VU 30 秒后用 10 秒降载；每名用户循环执行空闲查询、预约提交和统计查询，并在操作间保留 3 秒用户思考时间。P95 与业务错误阈值在整个场景中持续生效。
- 原因：容量目标是约 300 名并发在线用户。逐步到达并保持稳态能够覆盖真实连接、鉴权、事务和响应序列化压力，避免把所有用户强制同步到同一毫秒所产生的非业务惊群；该模型同时产生远多于单次 300 个请求的样本。
- 约束：负载仍使用真实 Nginx、后端和 PostgreSQL，不能缓存用户状态、绕过权限/事务/冲突检查或放宽开发文档中的 P95 阈值。
